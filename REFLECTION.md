# Reflection — Sprint 1 Demonstration Run

## What the harness did well
- **The contract caught a real defect that tests alone had missed.** The scaffold already had a `bulkStatus` implementation. Its tests passed, but it emitted `ACTIVITY_STATUS_CHANGED` **twice** per success: once through `update()` and once explicitly, with different payloads. That broke AC-07 ("exactly one event per success"). The Generator found it by auditing against the contract, fixed it (`activities.service.ts:56-59`), and added an exact-count regression test (`activities.service.test.ts:83-90`). Without an AC that named the event count, a status-code test would have passed. This is failure mode F3.
- **The approval gate and routing worked as designed.** There was one Planner pass, the developer typed `APPROVED`, the Evaluator wrote `VERDICT: PASS` on its first line (96.75), and the Monitor archived the run. It took 1 of 3 iterations, with no manual steps between agents.

## Where it fell short
1. **The Evaluator passed a module-boundary violation.** `src/reports/reports.service.ts:2` imported `ActivitiesRepository`, which breaks rule 2 (F1). `npm run arch:check` reported "no dependency violations (18 dependencies cruised)" because dependency-cruiser ignores **type-only** imports by default. The Evaluator's manual import check only covered `src/activities/*`, and it trusted the tool for everything else. The violation came from the scaffold, not from sprint 1, but the harness claimed HG4 was green when it wasn't. This directly weakens **Design Brief decision D2**: hard gates are only as deterministic as their configuration is correct. It was found in a post-run audit (`.harness/reviews/post-sprint-1-harness-audit.md`).
2. **Scores still depended on LLM judgement.** The Evaluator deducted 5 for branch coverage on a file the sprint didn't change. The verdict was unaffected, but the same inputs could have scored differently.
3. **The feature wasn't built from scratch.** The generated scaffold already had a first version of `bulkStatus`, so the run shows *governing and correcting* AI output more than greenfield generation. There is no separate Git baseline commit from before the run to diff against.
4. **Token cost is an estimate** (about 90–120k). Claude Code doesn't expose per-agent metering to the harness.

## Concrete improvements (1 done, 2 proposed)
1. **Done:** set `tsPreCompilationDeps: true` in `.dependency-cruiser.cjs` (the cruise now covers 39 dependencies instead of 18, and the violation is caught). Changed `ReportsService` to depend on `Pick<ActivitiesService,'list'>`. Added rules `no-direct-alerts-or-reports-service-coupling`, `reports-is-read-only` and `no-circular`. Made the route and shared coverage thresholds actually enforced in `jest.config.js`. Replaced free-form dimension scores with fixed deductions (`evaluation-criteria` §3).
2. **Next:** add a **mutation smoke test** for the gates. `scripts/gate-selftest.ts` would insert a known type-only cross-module import and a `throw new Error(` into a temporary copy, and assert that `evaluate-harness.ts` FAILs. It would run before each harness session, so a gate that silently stops detecting violations is caught before a sprint relies on it.
3. **Next:** have the Evaluator write `evaluator-feedback.json` (gate ID, result, file:line) next to the Markdown, so the Monitor's trend rule counts findings instead of parsing prose.
